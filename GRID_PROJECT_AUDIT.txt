1.1 ARCHITECTURAL PARADIGM
The existing application is structured as a 3-tier monolithic web system:
- Client Tier: Single Page Application (SPA) built with React 18 and Vite 5.
- API / Application Tier: RESTful service built with Spring Boot 3.3.4 and Java 21 LTS.
- Persistence Tier: Relational database running MySQL 8.0 in production/Docker, with an in-memory H2 database fallback for local rapid prototyping and automated testing.
- Edge / Reverse Proxy: Nginx 1.27 Alpine serving static frontend assets and reverse-proxying API requests (`/api/*`) and health probes (`/actuator/*`) to the backend container.

1.3 PROJECT STRUCTURE AND DIRECTORY LAYOUT
The project root contains three primary functional areas:
- `backend/`: Spring Boot Maven application containing domain entities, JPA repositories, transactional services, REST controllers, DTOs, security configurations, and JUnit integration tests.
- `frontend/`: React Vite SPA containing source assets, components, pages, routing, context providers, and API services.
- `selenium-tests/`: Standalone Maven module executing automated browser user journeys with Selenium WebDriver and JUnit 5.
- `deployment/`: Nginx reverse proxy configuration (`default.conf`), Dockerfile for frontend, systemd service descriptors, and deployment/rollback shell scripts (`deploy.sh`, `rollback.sh`, `health-check.sh`).
- `ansible/`: Configuration management playbooks, inventory definitions (`inventory.ini`), group variables (`all.yml`), and modular roles (`common`, `docker`, `app`, `nginx`).
- `docs/`: Comprehensive project documentation covering SRS requirements, agile sprints, problem statements, architecture, test plans, and evaluation checklists.

1.4 CURRENT APPLICATION FUNCTIONALITY
The platform is designed around managing team registrations for an implicit, single hackathon event:
- User Authentication: Secure login and session invalidation with pre-seeded demo accounts for three roles: ADMIN, ORGANIZER, and TEAM_LEAD.
- Team Roster Administration: Full CRUD lifecycle for teams (Team Name, Unique Code, Project Title, Description, Lead, Track).
- Member Management: Adding, updating, and removing individual team members (Full Name, Email, College, Department, Team Role) under each team.
- Deterministic State Machine: Enforces allowable status transitions (`DRAFT -> REGISTERED -> APPROVED -> IN_PROGRESS -> SUBMITTED -> COMPLETED`, plus `REJECTED`).
- Query Engine: Dynamic real-time search, multi-criteria filtering by track and status, pagination, and sorting.
- Analytics Dashboard: Visual KPI cards, status breakdown bar charts, track allocation distributions, and audit logging.

6. Missing Evaluations Interface: Organizers/Judges have no interface to score projects or view rubrics.

3.4 AUTHENTICATION & AUTHORIZATION ARCHITECTURE
- Session-Based Security: Uses `HttpSessionSecurityContextRepository` to maintain authenticated context across HTTP calls via the standard `JSESSIONID` cookie.
- Passwords: Encrypted using `BCryptPasswordEncoder(10)`. No plain passwords stored.
- CORS Configuration: Permits `http://localhost:*` and `http://127.0.0.1:*` with credentials enabled (`allowCredentials: true`) and pre-flight caching.
- CSRF Protection: Disabled (`csrf.disable()`) under the assumption of REST API usage with CORS isolation.
- Security Filter Rules: Public endpoints strictly limited to login, logout, health actuator, and H2 console. Method security (`@EnableMethodSecurity`, `@PreAuthorize`) protects mutation endpoints.

3.5 VALIDATION AND EXCEPTION HANDLING
- Central Exception Handling: `@RestControllerAdvice` in `GlobalExceptionHandler` intercepts domain exceptions and generates consistent RFC-style JSON error payloads (`ErrorResponse`).
- Handled Exceptions:
  - `ResourceNotFoundException` -> HTTP 404
  - `DuplicateResourceException` -> HTTP 409
  - `InvalidWorkflowException` -> HTTP 400
  - `UnauthorizedActionException` -> HTTP 403
  - `AccessDeniedException` -> HTTP 403
  - `BadCredentialsException` -> HTTP 401
  - `MethodArgumentNotValidException` -> HTTP 400 (with field-level validation error map)

SECTION 11 - PROBLEMS, ANTI-PATTERNS & TECHNICAL DEBT
================================================================================

11.1 CRITICAL ISSUES (MUST RESOLVE BEFORE GRID RESTRUCTURING)
1. Single-Hackathon Hardcoding: The data model and controllers completely lack the concept of a `Hackathon`. It is impossible to host multiple events, view past hackathons, or filter registrations by event.
2. Incompatible Role Architecture: Current roles are `ADMIN`, `ORGANIZER`, and `TEAM_LEAD`. The new GRID product specification mandates `TEAM`, `ORGANIZER`, and `SUPER_ADMIN`.
3. Loose Association of Team Lead: `teams.team_lead` is stored as an arbitrary text string matching username rather than a true Foreign Key to `users.id`. This prevents multi-team participation, user renames, or proper referential integrity.
4. Total Absence of Submissions & Evaluation Pipeline: There is no data model for project submissions (repo URL, demo URL, documentation, pitch deck, video) or judging rubrics and scores.
5. Missing Schema Migrations: Lack of Flyway or Liquibase means table alterations depend on Hibernate `ddl-auto=update`, which cannot drop obsolete columns or perform non-destructive schema migrations.

11.2 HIGH-PRIORITY TECHNICAL DEBT
6. Working Tree Pollution: 17 modified files remain uncommitted in the git working tree, including corrupted leading blank lines in `UserJourneysTest.java` and uncommitted edits to `Dashboard.jsx`.
7. Zero Frontend Automated Testing: No unit or integration test suite (Vitest/Jest) exists for the React SPA. Any UI restructuring has no automated test harness to catch regressions.
8. Monolithic Frontend Bundle: Lack of route-based code splitting (`React.lazy`) results in a single 664 kB JavaScript chunk, impacting initial page load performance.
9. Windows Service Docker Context Disconnect: When Jenkins executes as a native Windows service, it lacks access to the active user's Docker Desktop named pipe, necessitating defensive fallback commands that bypass true container deployment in CI.

11.3 ARCHITECTURAL & SECURITY CONCERNS
10. CSRF Protection Disabled: `csrf.disable()` is active in `SecurityConfig.java`. While standard for bearer tokens, session-cookie-based APIs (`JSESSIONID`) are vulnerable to cross-site request forgery without SameSite/CSRF tokens.
11. Inconsistent Branding: System names vary between `hackrbase`, `HTM DevOps`, and `Hackathon Team Management System`. Needs universal alignment to `GRID`.
12. Lack of User Administration UI: Super Admins cannot create, deactivate, or manage users via any frontend screen or backend endpoint.
